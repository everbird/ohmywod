## 1. 总体判断

**这是一个定位正确、已有真实使用积累的小工具；应该继续做“好用的 WoD 战报档案与阅读工具”，而不是做一个更像通用 SaaS 的网站。**

线上 `/usage` 显示约 1.21 万份当前战报、548 个目录、773 个账户、约 106.55 GB 的 JuiceFS 文件系统使用量。这证明项目有真实存档价值；观看次数则是请求计数，不宜当成真实用户数。

值得保留的选择：

- Flask + Jinja 多页面已经足够；没有理由为本项目引入 SPA 或复杂构建系统。
- 匿名可阅读分享链接、管理和上传需要登录，是恰当的权限模型。
- 目录管理、收藏、位置链接、移动浮窗都服务于真实 WoD 使用场景。
- Argon2id、历史密码惰性升级、限流、CSRF、路径 containment、ZIP 解压限额已有实际作用。
- 撤掉 AdSense，赞助页克制且有人情味；少量微信/支付宝支持者手工维护比接支付回调更合适。
- 应用代码与私有 ops 分离、版本固定、sops/age、恢复闸门、单机 DR 的方向适合个人维护。
- JuiceFS 已承担大量现有 HTML 文件，不建议为了“少一种组件”重写整套存储。
- PWA 只做安装和 standalone，不顺带引入离线缓存、后台同步、推送，是好的范围控制。

当前最需要改进的不是“再现代一点”，而是：**上传失败不能毁旧数据；阅读器安全和已有按钮必须可靠；找到目标战报的路径更短。**

## 2. 现在值得修的应用问题

### A1. 阅读器 HTML 清洗可被 `data-safe-*` 绕过【优先修】

位置：`ohmywod/ohmywod/views/report.py:42–89`，特别是 `:84–87` 的恢复逻辑；独立 reader 在 `:460` 起。

清洗函数将校验过的事件暂存进 `data-safe-*`，经过 Cleaner 后又把所有这类属性恢复成真实属性。但上传内容本来就可以带同名属性；`safe_attrs_only=False` 不会把它们当作私有标记清除。

隔离复现中，上传 HTML 的 `data-safe-onerror` 被恢复为 `onerror`。独立 reader 返回 200，HTML 中保留事件，且无 sandbox CSP。将实际 reader 输出放入本地浏览器，无害标记 `window.__review_xss` 自动变为 1。

这不是一般性的“要加强安全”：任意开放注册用户可上传内容，在访问者的**主站同源**运行脚本。原始 `/r/raw/...` 的 sandbox 做得对，但不能保护另一个将清洗内容直接嵌入的 reader。

该逻辑在 ops 固定的 `57a1e86` 中也存在，并非只属于 PWA 工作区。没有在线上传攻击样本。

**最小修法**：

1. 在输入阶段剔除所有上传内容自带的 `data-safe-*`。
2. 校验成功的事件记录在服务端内部结构中，或仅恢复由本次处理生成且属于固定白名单的标记；不要遍历用户属性无条件还原。
3. 同时检查 tooltip HTML 这条二次插入路径。
4. 补 malicious `data-safe-onerror`、正常 tooltip、正常层页跳转的回归测试。

不必为此迁移前端。后续若整理事件执行，把少数 WoD 函数和字面量参数转为受控数据/dispatcher，会比继续扩张任意 JS 的正则更清楚。

### A2. 坏 ZIP 同名重传会删除原战报【优先修】

位置：`ohmywod/ohmywod/views/upload.py:100–159`，特别是 `:134–140`。

当前上传直接面向正式 `tpath` 解压；遇到 `BadZipFile` 或 `OSError`，执行 `_cleanup_dir(tpath)`。这条路径可能早已存在，属于原来的战报，而不只是本次临时产物。

实际隔离复现：

1. 上传有效 `existing.zip` → 200，原文件存在。
2. 用同名文件提交无效 ZIP → 400。
3. 原文件被删除，数据库记录仍存在，原始阅读 URL → 404。

即使 ZIP 有效，直接叠加解压也可能混入上一次遗留文件；解压中途失败会影响旧版。

**最小修法**：ZIP 与解压结果各自使用本次上传的唯一临时路径，完成 ZIP/内容检查后再替换正式内容；失败只清理本次临时产物。需要覆盖时用同文件系统下的备份/重命名及失败回滚，不要直接对非空旧目录做无条件 `os.replace`。若暂时不想做覆盖流程，先拒绝同名覆盖也是可接受的简化。目录状态与路径复用也应一起检查，见第二轮 A6。

一起补一个便宜的内容检查：解压结果至少应包含可读的入口 `index.html`。当前仅包含 `readme.txt` 的 ZIP 也会返回 200、创建战报记录，随后阅读 404；这也已复现。

测试应断言“失败后原文件内容不变”，而不只是“坏 ZIP 返回 400”。

### A3. 阅读模式的统计“显示”按钮被清洗掉【下一轮修】

位置：同一清洗函数 `report.py:43–45`；`report_reader.html` 中有 `sd(rowid, activeRows)` 的实现。

实际线上页面：`/r/report/126/reader/2153119/statistics.html`。

原始版按钮事件是 `sd('...', ['activeRow_...', ...])`。当前参数正则允许字符串、数字、`this`、布尔值，却不允许字符串数组，因此 reader 中按钮的 `onclick` 消失。

对同一公开战报的浏览器对照：原始版点击后按钮由“显示”变“隐藏”；阅读模式点击仍为“显示”。这是已有功能回归，不是缺少一个 nice-to-have。

**建议**：修 A1 时同时补正常 WoD 参数类型的窄范围支持和真实样例测试。不要为了修“显示”而放宽成任意表达式。一个小型正常战报 fixture，比继续加很多“模板包含某字符串”的测试更有价值。

### A4. 收藏/点赞 UI 会把失败显示成成功【下一轮顺手修】

位置：`ohmywod/ohmywod/templates/report_details.html:286–318`。

点击后立即翻转 class 和图标，没有等后端成功，也没有失败回滚；计数继续使用服务端首屏常量。

本地浏览器拦截收藏请求、返回 500 后，按钮仍显示已收藏，而计数仍为 0。真实使用中用户可能以为战报已保存，之后找不到。

**建议**：请求中暂时禁用按钮；只在 HTTP 和业务状态都成功后更新；失败给一句可理解的提示并保留原状态。可以返回最新计数，也可以简单本地加减，不需要状态管理框架。

### A5. 原始战报 CDN 缓存与删除/覆盖语义冲突【明确取舍后修】

位置：`report.py:130–146`，`Cloudflare-CDN-Cache-Control` 的 86400 秒缓存；上传和删除路径没有对应的 CDN purge。

线上已实际看到 raw 子页 `cf-cache-status: HIT` 和 `Age`。因此即使源站已检查软删除，缓存命中时也不会走数据库检查。删除后的旧 raw 链接、同名覆盖后的旧内容可能继续被边缘缓存提供。

没有在生产执行删除/覆盖验证；后果按已确认的缓存存在与调用链推导。

这不要求工业级即时失效，但应有一个一致的产品承诺：若删除就是旧链接失效、覆盖成功就是新版可见，考虑最小按 URL purge、短一些的 TTL，或明确允许一个短暂旧缓存窗口。不要把“多数战报很少变化”误当成“战报永远不可变”。

## 3. 产品设计与日常使用

### 3.1 找战报应优先于找目录

“全部战报”实际上是目录列表，这个结构适合上传者管理，却不是读者的最终目标。548 个目录、55 页目录列表，默认首屏仍是早期目录。近期上传内容反而放在“使用情况”里。

高性价比改法：

- 全部目录页顶部直接放搜索框，不要求再去单独的搜索页。
- 给搜索提供一两条 WoD 示例词，如副本名、挑战名、团队名。
- 明确搜索范围：目前搜索文件名/显示标题/说明，不搜索整份战报正文和所有元数据。
- 搜索结果明确排序，例如更新/上传时间倒序加 ID 作为稳定次序，而非数据库自然顺序。
- 复用现有 `get_latest_reports()`，把最近上传放到真正的浏览入口；无需新增搜索服务。

先不要做精细职业/种族/装备过滤：当前许多结构化元数据为空，先解决标题与定位更划算。

### 3.2 长标题应该易读，而不是让用户解码文件名

搜索结果充斥 `wodlog_`、团队名、日期、等级等拼接，手机上标题占三四行，还重复“暂无描述”、编号和大多为零的互动数。

建议先做**展示层**格式化：保留原始文件名和路径，显示时弱化 `wodlog_`，优先呈现副本/挑战、等级、团队和日期。没有说明时省略占位行。零点赞/零收藏不必占据主要扫描空间。

现有手机卡片不是错误：它避免把桌面表格硬塞进手机。但可以更紧凑，例如标题两行、下一行所有者与日期；仍保留用户选择列表/卡片的能力。

### 3.3 匿名分享链路中不该突然要求登录

`report_details.html:22`、`category.html` 的面包屑“目录”链接到 `/r/`，该路由是登录后的我的主页。匿名读者从共享战报返回目录时会被送去登录。

把公开浏览路径的根面包屑指向 `/r/all` 或该上传者的公开目录；只有“我的”入口才指向 `/r/`。这是简单但直接影响分享体验的修正。

匿名收藏按钮现在只是灰掉。可以加“登录后收藏”的提示，并在登录后回到当前战报，不必先绕到我的主页。

### 3.4 首页/帮助的承诺应和实现一致

`landing.html:50` 仍写“在用户设置里切换阅读皮肤”，但 `ProfileForm`、`profile.html` 只有显示名称、邮箱、密码；reader 也固定加载 skin-4。

最简单是先删掉不存在的承诺，而不是为一句旧文案新增换肤功能。设置页标题中的“偏好设置”同样可以收窄。

首页与帮助共用说明，是合理复用，不必为了“两个页面应不一样”重写。若继续打磨：首页压缩为是什么、直接搜索/浏览、上传流程三个重点；详细导出说明留给帮助。匿名用户主按钮可写“登录并上传”，比“进入我的主页”更直白。

### 3.5 详情不要展示大量空字段

`report_details.html:146` 起展示很多元数据，其中不少为空；`default('-')` 不会把已定义的 `None` 换成横线。

没有详细元数据时，省略整块或只显示有内容的字段；少量必需字段用 `default('-', true)`。上传名称、排序等内部字段放次要位置，读者更关心副本、日期、分享者和说明。

### 3.6 阅读器是差异化核心，值得多花一点精力

层页、浮窗、锚点实际有用；不建议重做全部 WoD 原始内容。值得补的小点：

- 宽表局部横向滚动，导航和返回按钮保持在可视区域；加一个简短横屏提示。
- 信息型 tooltip 没有 `onclick` 时隐藏“前往”按钮。当前对示例战报的第一个说明浮窗点击该按钮，线上触发 `Cannot read properties of null (reading 'replace')`。
- 锚点点击实际正常，但复制提示最好中文；后续可用 Clipboard API 并判断是否成功，保留旧浏览器 fallback。
- 想增加功能时，阅读位置记忆比更多点赞指标更符合本项目用途；可以只用 localStorage，不做跨设备同步服务。

## 4. 视觉审美与移动端

### 做得好的

暗色底、克制的面板与清晰表单，比带广告的网页更适合长时间阅读。Logo、WoD 图和个人作者署名有辨识度，致谢页也不像商业转化页。**保留这些个人风格，不必换成一套无差别的“现代 SaaS 设计”。**

外层工具界面较现代、战报内容保持原游戏样式，并不天然矛盾；WoD 老玩家熟悉这些颜色和表格。

### 我的审美判断

目前略有“后台管理模板外壳 + 老游戏阅读器”的拼接感。主要原因不是暗色，而是：

1. `content-section → table shell → table row/card` 多层背景、圆角与边框叠加。
2. 335px 桌面侧栏、Logo 与 WoD 图有较强视觉重量；检索内容相对拥挤。
3. 表格链接绿、所有者青、按钮蓝，再加游戏内金/绿；关键操作焦点有些分散。
4. 悬浮位移、渐变分页、抬升卡片等装饰，对档案检索的价值有限。

优先“少一层框、少一点动画、少几个无效指标”，而不是继续加视觉效果。可以保持 Logo→导航→WoD 图片→账号的顺序，只调比例。链接与主动作明确职责即可，不必追求所有颜色完全一致。

手机列表的卡片间距可以缩小；桌面保留紧凑表格。个人页脚可以保留，但固定 2022 年和英文版权句可以顺手简化，不是优先项。

### 线上手机导航问题已经在本地修，不重复列成新需求

线上菜单按钮盖住标题，展开侧栏后内容被挤到右边，底部账号在 390×844 下不易看全。当前 PWA 工作区已有固定顶栏、遮罩侧栏、当前页面标记和高度分配调整，方向正确。

不要把这些修复再开一个“整站 UI 重设计”计划；完成真实内容和真机验收即可。

### 本地 PWA reader 仍有两个真实布局问题【发布前修】

用公开战报副本在隔离库验证了当前模板，而不是只用无战报的首页：

- 390px 手机视口，层页 `window.innerWidth=636`；统计页达 1560，body 宽度 1762。固定返回栏也分别扩展到 636/1560px，右侧“阅读模式”会落出手机可视区域。
- 返回栏默认 `box-sizing: content-box`，实测总高度 **69px**，但 `#page-border` 仅下移 **56px**，导致旧标题行上方约 13px 被遮挡。

最小修法：reader 控件局部使用 border-box 和一致的高度变量；导航宽度以实际可视宽度约束；将宽表约束到内容滚动区，不让它撑大整页与固定栏。

先不建议给独立 reader 随手加 doctype 或整体换布局：它仍沿用旧 WoD 滚动/尺寸机制，这类“格式清理”可能改变既有行为。

PWA 的真实安装、软键盘、横竖屏、浮窗与返回仍需要目标 Android/iPhone 验证。模拟视口、manifest 无解析错误、pytest 通过都不是完整安装验收。

## 5. ops Review

### 总体：方向正确，已经足够，不需要再堆架构

现有单机 + SQLite/Litestream + JuiceFS 元数据备份 + Redis db0 备份有清晰用途。版本固定、私有密钥、prepare/restore/serve 分离、挂载与 nginx 闸门，都值得保留。`reread → update web → restart web` 已正确覆盖配置变更和纯代码发布，并避免重启 Redis。

接受小窗口 RPO、没有防误删的独立对象备份，是项目已经做出的取舍；不建议本轮撤回并建设温备、双写、不可变备份或复杂恢复仪式。

真正需要的是让几个危险命令“不假成功、不误删”。

### O1. 停旧机关键写者失败仍继续切换【下次 DR 前修】

位置：`ohmywod-ops/scripts/dr-node:375–384`。

停旧机命令给 `systemctl disable --now ...` 和 `supervisorctl stop web` 都加了 `|| true`。因此关键停服失败也可能被当成“已停”，随后新机启动 Litestream、修改 DNS。Cloudflare 不立即切走的边缘还可能访问旧机；旧新复制进程也可能并存。

允许某个可选 timer 不存在很合理，但不能把 nginx/web/Litestream 的停止失败一起吞掉。

**最小修法**：关键操作不吞错误，或执行后明确确认旧 nginx、web、Litestream 不再运行，再晋升新机。可选监控失败继续 warning 即可。无需引入集群 fencing 系统。

没有执行真实停机。第二轮用完全离线 shell harness 将旧机两项停止操作模拟为失败，仍确认脚本 exit=0、到达新 Litestream 启动和 DNS PATCH；旧机仅 SSH 不可达也会继续。模拟中所有网络与服务操作都被替换，详见第 8 节 O1 补充。

### O2. `cleanup` 可以误删当前生产机或其他项目机器【下次 cleanup 前修】

位置：`dr-node:468–494`。

传入任意实例 ID/IP，都能查到后直接送给 DELETE API。没有判断是否是当前源站、上次切换的旧机、或属于本项目；`--yes` 还会跳过唯一的人类确认。

**最小修法**：删除前查询实际入口的源站 A 记录，拒绝删除当前生产 IP/ID；再检查本项目标签或最近一次 build/cutover 记录。保留显式人工例外用于清理失败候选机，但不要默认任意参数都合法。

顺手补一小段真正可执行的回退说明：旧机已 disable nginx/Litestream 等，仅把 DNS 改回并不足以恢复；脚本实际修改的是 apex A，错误提示里却写回 `DOMAIN` 的 A，而当前 `wod` 是 CNAME。无需完整 rollback 框架，一段准确的恢复服务与改入口命令即可。

### O3. 新构建不等于新备份【保留现有 RPO，但让信息准确】

位置：`dr-node:318–351`，`ansible/restore.yml:116`、`:203`、`:273`。

剩余问题：

### O5. 恢复闸门负向测试可假绿【顺手修测试】

### A6. 已删除目录仍接受上传，同名重建会串用旧内容【和 A2 一起修】

位置：`ohmywod/ohmywod/views/upload.py:57–65`、`:96–97`；`views/report.py:526–537`；`controllers/report.py:214–222`。搜索、收藏和 sitemap 的相关查询分别在 `controllers/report.py:314–362`、`:408–410`、`views/frontend.py:391–396`。

删除本身已经正确隐藏详情、reader 和 raw；问题是其他入口没有遵循同一个目录状态与物理路径约束。

隔离复现了三段相连的流程：

1. **删除目录后，原上传页面继续提交仍返回 200。** 新战报 `status=None`，父目录 `status=1`；详情、reader、raw 都返回 404，但搜索、最近上传和 sitemap 都将它列出，收藏接口也返回“收藏成功”，收藏页产生死链接。
2. **删除目录 A，再创建同名目录 B，系统分配新 ID，但继续使用相同的 `owner/category.name/report.name` 文件路径。** 新 ZIP 只有 `index.html`，旧 ZIP 的 `retired-level.html` 没有被清除；删除后该子页曾为 404，重建上传后又返回 200，新战报的 reader 也能读出旧子页。
3. **继续向已删除 A 上传同名 ZIP，会覆盖 B 的当前战报内容。** 请求仍返回 200；B 的战报记录还在，但实际 index 已变成通过 A 提交的内容。这不是跨用户权限绕过，而是同一用户的不同逻辑目录串用文件，足以造成误覆盖。

最小修法：

- 上传、编辑、排序等写入口拒绝已删除目录；新增点赞/收藏也应确认目标战报和父目录可见，取消收藏可保留清理历史的能力。
- 搜索、收藏、最近上传、sitemap 不只检查战报状态，也检查父目录状态。几处查询加上条件即可，不必重做权限架构。
- 创建同名目录时把历史已删除目录也纳入冲突检查。暂时提示换名是最简单的办法；若以后支持恢复，应明确恢复原目录，而不是悄悄创建第二条记录共用路径。
- A2 的正式替换不能叠加解压，成功替换后也不应残留旧版本的额外 HTML。

证据：`round2-repro.py`、`round2-repro-results.json` 的前三项。建议回归测试覆盖“删目录后继续上传”“删后同名重建”“重传减少子页”，而不只是分别测试删除/新建/上传都返回预期状态码。

### A7. 更换恢复邮箱无需旧密码，旧邮箱的重置链接仍有效【下一轮账号小修】

位置：`ohmywod/ohmywod/views/frontend.py:290–313`；`ohmywod/ohmywod/tokens.py:38–44`、`:67–72`。

当前旧密码只在修改密码时要求填写；只修改邮箱可以直接成功。而重置 token 仅绑定 UID 与密码 hash 的指纹，没有绑定恢复邮箱。

实际复现：先为旧邮箱对应的用户签发 token → 不填旧密码将邮箱改为新地址 → 旧 token 仍通过验证 → 用它重置密码成功。正常改密后 token 确实失效，这一点现有实现和测试是对的。问题窗口受到现有 **30 分钟**有效期限制，不是永久有效。

当邮箱承担密码恢复作用时，它不只是普通资料字段：已有会话可以直接更换恢复地址，旧邮箱持有的链接也不会因换邮箱失效。

建议只补两件便宜的事：**换恢复邮箱时要求当前密码；重置 token 同时绑定当前邮箱，换邮箱后使旧链接失效。** 不要求接邮件验证平台、MFA 或复杂账号系统。

证据：`round2-repro-results.json` 的 `email_change_reset_boundary`。没有发真实邮件；测试 token 的生成与线上邮件使用同一函数。

### A8. 找回密码后，之前登录的会话仍可写数据【若要支持账号找回，应补】

位置：`ohmywod/ohmywod/app.py` 的 `load_user()`；`controllers/user.py:66–74`；`models/user.py` 的 `UserMixin` / `password_updated_at`。

会话只记录用户 ID，加载时没有校验密码版本。找回密码改变了 hash、使旧密码和旧重置链接失效，但不撤销已经登录的浏览器。

隔离复现：客户端 A 用旧密码登录 → 独立客户端 B 用重置链接修改密码 → A 的 `/r/` 仍为 200，并成功创建新目录。测试请求没有共享 app context，因此不是测试夹具的登录缓存泄漏。

若“找回密码”只为忘记密码使用，这个行为未必马上造成事故；若它也被当作账户失控后的恢复手段，旧会话仍可删除/上传战报，恢复就不完整。

最小改法：复用已有 `password_updated_at`，登录会话记录并在加载时校验密码版本，改密/重置后要求旧会话重新登录。注意不要把自动升级旧 hash 的正常登录误当作攻击；在成功升级后签发新版本会话即可。无需新增会话表或 Redis 登录中心。

证据：`round2-repro-results.json` 的 `session_survives_password_reset`。

### A9. 赞助 API 失败虽能回退，但每次访问仍重新等待失败【低优先级，顺手修】

位置：`ohmywod/ohmywod/afdian.py:238–272`、`:309–342`。

last-good 的回退是有效的，赞助页没有因普通网络错误变成 500；但失败分支没有写短期缓存或重试冷却。fresh 一过期，之后每个请求都同步查询订单和赞助 API，再回退旧数据。

模拟两条 API 都不可达时，连续访问 3 次 `/thanks`：3 次都返回 200、都显示 last-good，但发生 **6 次远端尝试**，每项 timeout 配置为 5 秒。模拟立即抛错，没有实际等 10 秒；在两条查询都等到超时的场景，页面可能约 10 秒后才显示旧数据，且下一位访问者重新等待。

建议失败后将 last-good/空结果作为短期 fresh 缓存 30–60 秒，或记录短冷却时间。现有同步实现可继续保留，不需要为非核心赞助墙引入 Celery 或后台刷新架构。

证据：`round2-repro-results.json` 的 `sponsor_outage_retries_every_page`。

### O7. 候选机和保留旧机仍在向同一桶备份 JuiceFS 元数据【下次 DR build 前修】

这是第二轮最重要的运维新增，不是对已接受 RPO 的苛求。

仓库链路：

- `scripts/dr-node:228–230` 启动候选机时只关闭 Litestream、监控和 db0 备份，没有关闭 JuiceFS 自动备份。
- `ansible/roles/juicefs/defaults/main.yml:18` 默认 `juicefs_backup_meta: "1h"`；`templates/juicefs.service.j2:14` 将其传给 mount。
- `dr-node:384–385` 切换时停旧 nginx/web/Litestream 等，却明确保留旧 JuiceFS 挂载。
- 两台机器分别使用 `redis://localhost:6379/2` 的独立元数据副本，同时沿用同一个卷名、bucket 和 `rstore/meta/` 备份前缀。
- `scripts/s3-meta.py` / `restore.yml` 按对象 LastModified 选最新 dump，没有区分哪个节点产出的元数据。

已离线渲染确认：候选配置仍是 `juicefs mount ... --backup-meta 1h --cache-size 5G`。并核对固定 **v1.3.1** 的上游源码：

- [cmd/mount.go:409–412](https://github.com/juicedata/juicefs/blob/v1.3.1/cmd/mount.go#L409-L412)：非 read-only、非 no-bgjob、间隔大于零时启动备份任务。
- [pkg/vfs/backup.go:50–95](https://github.com/juicedata/juicefs/blob/v1.3.1/pkg/vfs/backup.go#L50-L95)：用本地元数据引擎中的 `lastBackup` 判断是否到期；不要求本轮发生业务写入，两份独立 Redis 不能互相协调这个状态。
- 同文件 `:100–165`：向对象存储上传带当前时间的 dump，成功后还执行备份轮转。

因此候选机在等待切换时、旧机在稳定观察时，都可能把落后的元数据重新写成一个时间更新的对象。下次 restore 的“最新备份”可能来自候选/旧机，而非当前生产，**文件上传时间新，并不表示数据恢复点新**。这比已明确接受的定时备份 RPO 更危险：它混淆了恢复链的数据来源。

用实际 `s3-meta.py` 和 fake ListObjectsV2 XML 也确认：较新上传、但 payload 代表较旧候选副本的对象会被选为 latest。**没有启动真实 JuiceFS 挂载、向实际桶写备份或运行 DR**；实际生产是否曾出现这种对象混写，本次未验证。

最小修法：

1. 候选机显式使用 `--backup-meta 0`；最好同时禁用其他后台维护任务或采用只读挂载，候选自检只需读取。不要只停止监控——监控不负责产出备份。
2. 晋升时先停止旧 JuiceFS 挂载/后台任务；保留 Redis/SQLite 数据即可，回退时重新挂载。新机再恢复正常生产挂载与备份参数。
3. 确认**实际进程**参数已改变。当前 juicefs role 改 unit 只 daemon-reload、`state: started` 不重启已有 mount；需要受控重启，并按现有 BindsTo 关系恢复 nginx，而不是只把模板改绿。
4. 轻量补候选/生产两种 ExecStart 的渲染断言和晋升检查，无需做集群锁或另一套备份平台。

特别注意关闭参数：上游 [cmd/flags.go:269–272](https://github.com/juicedata/juicefs/blob/v1.3.1/cmd/flags.go#L269-L272) 的 mount 默认就是 **1h**。当前 Jinja 模板中，空字符串或数值 `0` 都会省略整个参数，仍回到自动备份；要输出 `--backup-meta 0`，应传字符串 **`"0"`**，或修模板使显式零值也被渲染。

证据：`round2-juicefs-check.py`、`round2-juicefs-results.json`；下载到 `/tmp` 的 `juicefs-v1.3.1-{mount,backup,flags}.go` 保留了源文件与 SHA256。

### O1 补充：失败与 SSH 不可达均未阻断晋升【下次 cutover 前修】

第二轮不再只看 `|| true`，而是执行真实 `cmd_cutover()` 控制流、替换所有外部动作：

| 完全离线场景 | 结果 |
|---|---|
| 旧机 systemctl 和 supervisorctl 都返回失败 | 脚本仍声称旧写者已停，继续到新 Litestream 启动与 DNS PATCH，最终 exit=0。 |
| 旧机 SSH 返回不可达 | 脚本警告并跳过停止/追平，仍继续到新 Litestream 启动与 DNS PATCH，最终 exit=0。 |

第二项不是“灾备时永远不能跳过死旧机”：真正已停机的旧节点当然可以显式跳过。问题是 **SSH 不可达不等于旧 web、Litestream 和 JuiceFS 都已停止**；可能只是管理端口、登录或网络路径出问题。

建议关键停止失败立即中止；旧机无法确认时要求操作者明确允许“旧节点已停止/隔离”的灾难场景，而不是默认推定已死。处理 db0 备份时也注意停 timer 不会结束已经运行的 oneshot `backup.service`。保留人工明确的灾备例外，不引入复杂自动 fencing。

证据：`round2-dr-mock.py`、`round2-dr-results.json`、两份 `round2-dr-*.log`。模拟中的成功公网探针也是 fake，不能解读为真实切换验收。
