# 微信打赏手工致谢计划

> 本文记录战报网把“微信打赏码过来的赞助者”加入致谢页的低成本方案。当前结论：**先不做微信支付商户 API，不做后台 CRUD，不写 SQLite；用配置维护少量手工赞助者，并在致谢页与爱发电赞助者合并展示，用来源 icon 区分渠道。**

## 1. 背景与结论

战报网已有爱发电入口与只读赞助者墙。微信侧目前适合作为“打赏码收款”渠道，而不是自动化支付集成渠道。

个人微信打赏码本质上只是二维码图片，站点侧通常拿不到可靠的服务端回调、付款人昵称、备注和订单状态。若为了自动上墙改接微信支付商户 API，需要商户号、证书/密钥、下单、回调验签、订单幂等、退款与异常对账等长期维护。对个人兴趣项目来说，这个复杂度明显高于收益。

因此当前选择：

- 微信打赏码继续用于收款入口。
- 微信来源赞助者较少时，用本地配置手工维护致谢名单。
- 致谢页合并展示“爱发电自动名单 + 微信手工名单”，并在名字前追加来源 icon 区分渠道。
- 配置中保留微信赞助金额与赞助时间，作为内部维护信息；前台不展示金额和时间。
- 不记录真实身份信息，不承诺任何功能权益。
- 等微信来源赞助明显增多、配置维护开始变烦时，再重新评估后台 admin CRUD。

## 2. 范围

### 2.1 本阶段要做

- 新增一个配置项承载微信手工赞助者名单。
- 每条记录包含展示名、来源、是否显示、内部金额和赞助时间。
- 致谢页读取配置名单，并与现有爱发电名单合并展示。
- 致谢页通过来源 icon 区分爱发电和微信赞赏码。
- 保持匿名默认与隐私口径一致。
- 给测试覆盖配置解析、匿名化、隐藏项过滤和页面渲染。

### 2.2 本阶段不做

- 不接微信支付商户 API。
- 不做支付回调、订单核验、退款处理或自动对账。
- 不做后台 admin 页面。
- 不新增 SQLite 表、模型或 migration。
- 不在前台展示金额或赞助时间。
- 不记录付款截图、微信昵称、微信号、手机号等可反查身份信息。
- 不开放任何公开提交入口。

## 3. 数据形态建议

配置项名建议为 `MANUAL_SPONSORS`，放在运行时配置中。微信来源赞助者较少时，直接改配置并重启/重载应用即可。

建议数据形态：

```python
MANUAL_SPONSORS = [
    {
        "display_name": "某某",
        "source": "wechat",
        "amount": "20.00",
        "sponsored_at": "2026-08-05",
        "visible": True,
    },
    {
        "display_name": "匿名",
        "source": "wechat",
        "amount": "10.00",
        "sponsored_at": "2026-08-05",
        "visible": True,
    },
]
```

字段说明：

- `display_name`：前台展示名。空白、缺失或填“匿名”时统一显示为“匿名支持者”。
- `source`：来源标记，当前手工配置只需要 `wechat`。前台用 icon 区分来源，不展示原始字段文本。
- `amount`：微信赞助金额，内部维护使用；前台不展示。建议用字符串保存，避免浮点精度和格式化差异。
- `sponsored_at`：赞助时间或日期，内部维护使用；前台不展示。建议使用 `YYYY-MM-DD`，需要更精确时用 ISO 8601。
- `visible`：是否显示，默认建议为 `True`；设为 `False` 时隐藏但保留记录。

可选但暂不推荐的字段：

- `note`：内部备注，仅用于维护者自己识别，不进前台。

金额和赞助时间只作为站长内部维护信息，不进入模板上下文里的公开展示字段；若后续做后台，也应继续默认隐藏。

## 4. 展示与隐私规则

- 前台致谢页展示来源 icon + 名字 chip：爱发电和微信赞赏码用不同 icon 区分。
- 前台不展示金额、赞助时间、备注或任何可反查身份的信息。
- 优先尊重对方明确备注的展示名。
- 对方没有明确展示名时，显示“匿名支持者”。
- 配置中的名字必须经过与爱发电昵称相同的模板转义路径，避免 XSS。
- 来源 icon 应使用站内已有 Font Awesome，例如爱发电用 `fa-mug-hot`，微信赞赏码用 `fa-qrcode` 或 `fa-heart`；icon 需带可访问文本或 `title` / `aria-label`。
- 合并展示时可以保留重复名字；若后续重复明显影响观感，再加去重策略。
- 不因为赞助提供功能权益，不在页面文案中暗示付费换功能。

## 5. 实现方向

### WMS-001 — 新增配置读取与规范化

- 状态：`todo`
- 优先级：`P1`
- 依赖：无
- 最后更新：2026-08-05

方向：

- 在配置中增加 `MANUAL_SPONSORS = []` 默认值。
- 新增一个小函数，例如 `manual_sponsor_entries()`，从 Flask config 读取列表并输出已规范化的展示条目。
- 过滤 `visible is False` 的项。
- 把缺失、空白、`匿名` 统一映射成既有的 `匿名支持者`。
- 保留 `amount` 与 `sponsored_at` 供内部维护，但不要把它们传给前台展示模板。
- 输出结构应包含 `display_name` 与 `source`，供致谢页选择 icon。
- 对畸形配置 fail-soft：跳过非 dict 项或无法解析项，页面不能 500。

完成判断：

- 未配置时返回空列表。
- 配置若包含正常、匿名、隐藏、畸形条目，输出稳定且不抛错。
- 前台展示数据不包含金额和赞助时间。

### WMS-002 — 合并到致谢页

- 状态：`todo`
- 优先级：`P1`
- 依赖：WMS-001
- 最后更新：2026-08-05

方向：

- 复用现有 `/thanks` 页面。
- 将爱发电结果与微信手工结果合并成统一条目列表，每条至少包含 `display_name` 与 `source`。
- 致谢页在名字前显示来源 icon：爱发电和微信赞赏码视觉可区分。
- 空态文案可微调为“还没有可展示的赞助者”，避免只提爱发电。
- 页面说明增加一句：微信打赏来源的致谢名由站长按备注手工维护。

完成判断：

- 只有爱发电名单时行为不变。
- 只有微信手工名单时致谢页正常显示。
- 两者都有时合并展示。
- 爱发电与微信来源在同一列表中通过 icon 区分。
- 所有第三方输入都经过模板自动转义。
- 页面不展示金额和赞助时间。

## 6. 以后什么时候升级到后台

满足任一条件时再重看后台 admin CRUD：

- 微信来源赞助者达到配置维护明显费事的程度。
- 需要在手机上随时增删，而不是通过部署配置更新。
- 需要多人维护名单。
- 需要查看历史、隐藏/恢复、审计操作。

若升级后台，仍建议保持克制：

- 只开放管理员使用。
- 字段仍以 `display_name`、`source`、`amount`、`sponsored_at`、`visible`、`note` 为主。
- 默认不展示金额和赞助时间。
- 后台数据进入 SQLite 后，需要明确接受其进入备份/恢复链。
